# Online Shop

Order management system for an e-commerce process, developed as part of CSS-3008 Corporate Development labs.

## Project Overview

Online Shop manages orders through a controlled lifecycle. It demonstrates business rule validation, Spring Boot dependency injection, JPA/Hibernate persistence, Flyway database migrations, and transaction management.

**Order lifecycle:**

`CART → PAID → SHIPPED → DELIVERED`

A return is handled as a separate process.

## Business Rules

| From | To | Allowed? |
|---|---|---|
| `CART` | `PAID` | Yes |
| `PAID` | `SHIPPED` | Yes |
| `DELIVERED` | `RETURNED` | No |
| `SHIPPED` | `CART` | No |

### Forbidden Transitions

1. **`DELIVERED → RETURNED`** — A delivered order cannot be returned directly. It must go through a separate return process.
2. **`SHIPPED → CART`** — A shipped order is already in logistics and cannot be moved back to the cart.

## Architecture

The project separates business rules, application logic, persistence, and outbound integrations.

- **`domain`** — Order statuses, identifiers, business rules, and domain exceptions. Domain classes remain plain Java and do not import Spring, JPA, or Hibernate APIs.
- **`handler`** — Application services that coordinate order operations.
- **`persistence`** — JPA entity, Spring Data repository, and a persistence adapter that talks to PostgreSQL through Hibernate.
- **`outbound`** — Implementations of outbound ports, such as order notifications.
- **`config`** — Application entry point and Spring bean configuration.

### Spring Integration

`Application` starts the Spring Boot application. It scans the whole `org.example` tree and explicitly enables JPA repositories and entity scanning for the `org.example.persistence` package.

`OrderService` is registered as a Spring `@Service` and receives its dependencies through constructor injection.

The `Rule` bean is configured in `Config`. `TransitionRule` and `ForbiddenRule` are combined through `RuleChain` and injected into `OrderService` through the `Rule` interface.

### Rule Chain

- `TransitionRule` validates the normal order lifecycle.
- `ForbiddenRule` blocks forbidden business transitions.
- `RuleChain` combines the rule implementations.

The domain layer does not depend on Spring. Framework-specific configuration and annotations remain at the application boundary.

## Database and Persistence

PostgreSQL stores orders in the `shop_order` table. The schema is owned by **Flyway**, and **Hibernate** only maps entities to it and validates that the mapping matches.

| Column | Purpose |
|---|---|
| `id` | UUID primary key |
| `business_key` | Unique business identifier for an order |
| `status` | Current order status (stored as text) |
| `title` | Order title |
| `created_at` | Creation timestamp generated by PostgreSQL |

Database constraints enforce data integrity:

- `PRIMARY KEY` ensures each order has a unique ID.
- `UNIQUE` prevents duplicate business keys.
- `NOT NULL` requires mandatory fields.
- `CHECK` restricts status values to `CART`, `PAID`, `SHIPPED`, `DELIVERED`, and `RETURNED`.

### Flyway Migrations

Schema changes are versioned SQL scripts in:

`src/main/resources/db/migration/`

| Migration | Purpose |
|---|---|
| `V1__create_shop_order.sql` | Creates the `shop_order` table with all constraints |

Flyway runs automatically on application startup and applies every migration that has not been applied yet. Applied migrations are recorded in the `flyway_schema_history` table. An already applied migration must never be edited; any schema change is a new `V<n>__description.sql` file.

The project uses `flyway-core` together with `flyway-database-postgresql`, which Flyway 10+ requires for PostgreSQL.

### JPA / Hibernate Mapping

- **`OrderEntity`** — JPA entity mapped to `shop_order` with `@Entity`, `@Table`, `@Id`, and `@Column`.
  - `status` uses `@Enumerated(EnumType.STRING)`, so values such as `CART` and `PAID` match the `CHECK` constraint.
  - `created_at` is `insertable = false, updatable = false` because the value comes from the database default `now()`.
- **`OrderJpaRepository`** — Spring Data `JpaRepository<OrderEntity, UUID>`. Spring generates the implementation, including the derived queries `findByBusinessKey` and `countByBusinessKey`.
- **`OrderJpa`** — persistence adapter used by the service layer. It provides operations to:
  - Insert an order (`persist` followed by `flush`, so the `INSERT` runs immediately and a duplicate is detected inside the method).
  - Count orders by business key.
  - Find an order's status.

### Configuration

`src/main/resources/application.yml`:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/css
    username: css
    password: css
  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate   # Flyway owns the schema, Hibernate only validates it
  flyway:
    enabled: true
    locations: classpath:db/migration
```

`ddl-auto: validate` makes the application fail at startup if an entity no longer matches the schema created by the migrations.

## Transaction Management

`OrderService` uses `@Transactional` for order registration operations.

- `register()` inserts an order and invokes the notification port.
- `insertTwice()` attempts two inserts with the same business key within one transaction.

If the second insert fails with the unchecked `DuplicateOrder` exception, Spring rolls back the transaction. Neither insert should remain in the database.

Separate registration calls demonstrate duplicate handling: the first successful registration remains committed, while a later duplicate registration fails without removing the original row.

## Testing

The test suite covers business rules, application behavior, database persistence, and transaction rollback.

- `OrderPolicyTest` — business rules, plain unit test.
- `OrderServiceTest` — service logic with Mockito mocks, no Spring and no database.
- `OrderDatabaseTest` — `@SpringBootTest` against real PostgreSQL. Flyway creates the table on startup, each test truncates it first. Covers rollback, duplicate handling, enum round trip, `CHECK` and `NOT NULL` constraints.

Database tests need a running PostgreSQL:

```bash
docker compose up -d
mvn -q verify
```

## Running the Application

### 1. Start PostgreSQL

```bash
docker compose up -d
```

This starts PostgreSQL 16 with database `css`, user `css`, password `css` on port `5432`. The application itself is not run in Docker.

### 2. Start the Application

```bash
mvn spring-boot:run
```

On startup Flyway applies the migrations from `db/migration`, then Hibernate validates the entity mapping.

### 3. Run Tests

```bash
mvn -q verify
```

## Lab Scope

The project evolves step by step:

- **Lab 2** — plain Java business rules and Spring Boot integration.
- **Lab 3** — JDBC persistence and transaction management.
- **Lab 6** — Spring Boot JPA and Hibernate replace the JDBC repository.
- **Lab 7** — Flyway takes over schema management from manual SQL.

The application does not require a REST API for these labs.
